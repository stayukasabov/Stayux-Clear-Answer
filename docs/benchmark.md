# Benchmark: Clear Answer off versus on

Generated by `python3 scripts/bench.py report`. Method and limits are at the end of this page.

**Status: pilot only.** These numbers come from 2 tasks (c1, d1) on Haiku and
Sonnet, one run each. The full run (20 tasks, 3 models) was not done. Anyone can
run it with `python3 scripts/bench.py run`, then `judge`, then `report`.

What the pilot found:

- The gate works: lint errors fall to zero in every gated answer.
- Gated answers are more compact, from about the same length (Sonnet chat) to
  about a quarter of the length (Haiku procedure).
- On procedures, the compact answers drop content. The judge scored them 2 out
  of 5 for facts kept, against 4 or 5 without the skill. Examples of dropped
  content: a rollback step, and a test of the new key before rollout.
- The cut happens in the first draft, not in the gate. The draft passes the
  linter on the first try, so the linter never removes text.
- The pilot found and fixed two plugin bugs: strict mode had no linter
  command, and a session that could not read the rule files skipped the gate.
- An earlier skill version (0.2.0, before the "translation, not summary"
  wording) scored 2 out of 5 on chat as well. Raw data:
  `bench/results-pilot-0.2.0/`.

Clear Answer aims for compact answers. The judge measures facts kept against the
longer answer, so it also counts some extra detail as lost. The dropped safety
steps are a real loss.

## Method

- Tasks: `bench/tasks.json` (10 chat questions, 5 write tasks, 5 rewrite tasks).
- Writers: Claude Haiku, Sonnet, and Opus through `claude -p` on a Claude Pro plan.
- Off: `claude -p "<task>" --model <m> --tools "" --setting-sources "" --no-session-persistence --output-format json`, in a new empty directory.
- On: two turns, as a user would do it. Turn 1 is `/clear-answer:on` (chat) or `/clear-answer:mode strict` (documents). Turn 2 resumes that session with the task. Both turns add `--plugin-dir <repo> --add-dir <repo> --tools Bash,Read --allowedTools "Bash(python3:*)"`. Only turn 2 is measured.
- Lint metrics: `scripts/ste_lint.py` with the seed dictionary only. Chat tasks use the `chat` profile, document tasks the `full` profile.
- Judge: a different Claude model from the writer (Opus judges Haiku and Sonnet, Sonnet judges Opus). It sees the request, the original text for rewrite tasks, and the two answers as Text A and Text B in a random order. It does not see the rules or which answer used the skill. Its rules are in `JUDGE_SYSTEM` in `scripts/bench.py`.
- Raw prompts, outputs, and judge answers: `bench/results/`.

## Limits

- All writers and the judge are Claude models. The judge never scores its own output and does not know which answer used the skill, but a same-family bias is possible.
- `claude -p` has no temperature option. Runs on a subscription plan are not exactly repeatable. The raw outputs are saved so that anyone can check the numbers.
- The results apply to these three Claude models, not to all models.
- The lint metrics use the same linter that the skill uses as its gate, so they favour the on condition by design. The judge score is the independent check.

## Gate cost cut (0.9.1, 2026-10-13)

Changes: brief lint output (`--brief`), rechecks with only the changed
sentences, and no extra rule files to read. Real runs with Claude Sonnet, one
run each, before and after the change:

| Task | Output tokens before | Output tokens after | Cost before | Cost after |
|---|---:|---:|---:|---:|
| 502 question, Clear Answer on | 1,640 | 1,558 | $0.246 | $0.238 |
| `/clear-answer:explain` (CDN) | 1,033 | 954 | $0.197 | $0.198 |

The saving is small, about 5 to 8% of output tokens. In both runs, the first
check passed, so the smaller rechecks did not apply. Most of the cost is the
Claude Code context (about 45,000 to 96,000 cached input tokens for each run),
and the second copy of the answer. The check before the reply needs that copy.
These are single runs, so treat them as an indication.
